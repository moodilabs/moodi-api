# PR 생성 스킬

## 설명

현재 브랜치의 변경사항을 분석하여 PR을 생성한다.

PR은 코드 변경 목록이 아니라 **기능과 구현 의도를 설명하는 문서**로 작성한다.

리뷰어가 git diff를 보지 않아도 변경 목적과 영향 범위를 이해할 수 있도록 작성한다.

## 참고 파일

- `CLAUDE.md` — 프로젝트 컨벤션 및 아키텍처
- `.github/pull_request_template.md` — PR 템플릿 원본
- `CLAUDE.md > API 문서` — DocsTest 작성 후 adoc 파일·index include 체크리스트

## 절차

1. `git status`로 작업 상태 확인
2. `git log develop..HEAD --oneline`으로 커밋 확인
3. `git diff develop...HEAD`로 변경사항 분석
4. 변경사항을 **기능 단위**로 재구성
5. PR 제목 작성
6. PR 본문 작성
7. 사용자에게 제목/본문 확인받기
8. 승인 후 `gh pr create`

## PR 제목 규칙

- 커밋 컨벤션을 따른다: `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `test:`, `style:`
- 70자 이하
- 변경사항의 핵심 기능을 제목으로 작성
- 커밋 제목을 그대로 복사하지 않는다


## PR 작성 원칙

### 작업 내용

작업 내용은 **가독성**을 최우선으로 한다. 빽빽한 산문 대신, 구조화된 형태로 작성한다.

**구조:**
1. 첫 문단에 **왜** 이 작업이 필요했는지 (기존 문제) 간결하게 쓴다 — 1~2문장.
2. "이를 해결하기 위해 …" 로 이어서, 해결책이 여러 개면 **번호를 붙여 나눈다** (`**1) 제목**`, `**2) 제목**`).
3. 각 해결책 안에서 세부 사항은 **불릿(`-`)** 으로 나열한다.
4. 구현 판단이나 주의사항은 **인용(`>`)** 으로 분리한다.

**주의:**
- 클래스명·메서드명을 남발하지 않는다. 역할이나 맥락으로 표현한다. 예) `ChatCompletionResponse.extractContent()` → "공통 응답 DTO에 통합".
- 한 문단이 5줄을 넘기면 불릿이나 소제목으로 쪼갠다.
- 후속 작업이 있으면 마지막에 짧게 언급한다.


### 변경사항

변경사항은 **파일 단위가 아니라 기능 단위**로 작성한다.


### API 스펙 (REST API 추가/변경 시)

REST API가 추가되거나 변경된 경우에만 작성한다. 내부 리팩토링, 설정 변경, 인프라 작업에서는 작성하지 않는다.

| 항목 | 값 |
|---|---|
| Method | `GET` / `POST` ... |
| Path | `/api/v1/...` |
| 파라미터 1 | 타입, 필수/선택, 제약 |
| ... | ... |

시나리오별 응답:

**정상** — `요청 예시`
```json
HTTP 200
{ ... }
```

**검증 실패** — `요청 예시`
```json
HTTP 400
{ "error": { "message": "..." } }
```

### DB 스키마 변경 (Flyway 마이그레이션 추가/변경 시)

Flyway 마이그레이션이 추가되거나 변경된 경우에만 작성한다. 테이블/컬럼/인덱스 변경이 없으면 생략한다.

| 마이그레이션 | 변경 내용 |
|---|---|
| `V{N}__{name}.sql` | 테이블명, 컬럼(타입), 제약조건, 인덱스를 포함하여 구체적으로 기술 |

### 테스트 결과

실제로 수행한 검증만 작성한다. 

- [x] `./gradlew test` 통과 (N tests, 0 failed)
- [x] [수동 검증 항목]
- [ ] [리뷰어가 검증할 항목]

### 관련 이슈


## 작성 규칙

1. PR 제목은 커밋 컨벤션을 따른다 (feat:, fix:, chore: 등)
2. 변경사항을 커밋 단위가 아니라 **기능 단위**로 정리한다.
3. 작업 내용은 변경 이유와 구현 방식을 설명한다. 단순 요약만 작성하지 않는다.
4. 리뷰어가 확인해야 하는 내용이 있다면 작업 내용에 포함한다.
5. 파일 변경 목록을 그대로 나열하지 않는다. 반드시 기능 중심으로 작성한다.
6. REST API 변경이 없는 경우 API 스펙/응답 예시 섹션은 생략한다.
7. 본문은 **리뷰어를 위한 문서**라는 관점으로 작성한다. git diff를 읽기 전에 전체 변경사항을 이해할 수 있도록 작성한다.
8. Flyway 마이그레이션이 포함된 경우 DB 스키마 변경 섹션을 반드시 작성한다. 컬럼 타입, 제약조건, 인덱스를 구체적으로 기술한다.
9. base 브랜치는 `develop`을 기본으로 한다.
10. **가독성 우선**: 긴 산문 덩어리를 쓰지 않는다. 소제목·번호·불릿·인용을 적극 활용하여 시각적으로 구분한다.
