# 출시 전 점검 — 백엔드·기획·디자인 문제 정리

작성일 2026-09-16. 대상: moodi 앱(Expo/React Native) + moodi-api(Spring Boot) + `moodi.kr` 정적 페이지 + MOODI_Design(Figma).

## 검증 방법

기획서·디자인만 읽고 적은 항목은 없다. 모든 항목은 아래 중 하나 이상으로 확인했다.

- `dev-api.moodi.kr` 실호출(응답 본문·상태코드를 그대로 인용)
- 백엔드 소스 확인(파일:줄)
- 웹 빌드(`localhost:8081`)를 Playwright로 구동해 실제 렌더 결과 확인
- 안드로이드 에뮬레이터 화면 캡처
- Figma 프레임 캡처와 실제 화면 대조

런타임으로 재현하지 못한 항목은 **미검증**으로 표시했다. 판단이 갈리는 곳은 "어느 쪽이 맞는가"를 명시했다.

## 1. 출시 차단

### [B1] 공개 개인정보처리방침·계정삭제 페이지가 실제 삭제 동작과 정반대다

`moodi.kr/privacy`와 `moodi.kr/account-deletion`은 "탈퇴해도 북마크·루트·사진추천 기록을 보관하며 재로그인하면 복구된다"고 기술한다. 코드는 정반대로 동작한다.

| 항목 | 페이지 기술 | 실제 동작 | 근거 |
|---|---|---|---|
| 북마크 | "Restored with your account" | **하드 삭제** | `BookmarkWithdrawalListener.java:18-21`, `bookmark` 테이블에 `deleted_at` 컬럼 자체가 없음(`V4__create_bookmark.sql:1-10`) |
| Pick(사진추천) + 업로드 원본 | "Tied to your account record" | **하드 삭제**(GCS 사진 포함) | `PickWithdrawalListener.java:33-49` |
| 루트 | "your bookmarks and routes come back" | 소프트 삭제 후 **영구 접근 불가** | `RouteJpaRepository.java:41-44`, 모든 `publicId` 조회가 `deletedAt IS NULL` |
| 공유 링크 | "stay reachable to anyone holding the link" | 탈퇴 즉시 `ROUTE_NOT_FOUND` | 위와 같음 |
| 복구 범위 | "재로그인하면 복구" | `Member.restore`는 `deletedAt` 해제 + email 설정 **2줄이 전부** | `Member.java:120-123` |

실제로 남는 것은 `provider`/`providerId`와 `feed_impression` 두 가지뿐이다.

**왜 차단 사유인가** — 이 URL이 Play Console / App Store에 제출하는 개인정보처리방침 URL이고, 앱 안에서도 "Read the full Privacy Policy"로 링크된다(`TermsDetailScreen.tsx:59,73-75`). 즉 앱 내 문서가 이 허위 진술을 참조로 승계한다. 반면 **앱 내 탈퇴 플로우 문구는 정확하다**(`DeleteAccountFlow.tsx:162-164,223-225`) — 틀린 쪽은 웹 페이지다.

**오염원** — `moodi-api/src/main/java/com/moodi/member/CLAUDE.md:231-243`이 아직도 `bookmark · route · feed_impression · pick_request`를 "유지"로, 탈퇴를 "복구 가능한 비활성화"로 적고 있다. 웹 페이지 문구가 여기서 파생된 것으로 보인다. 이 문서부터 고쳐야 같은 오류가 재발하지 않는다.

**제품 결정 필요** — 둘 중 하나를 골라야 하며, 임의로 정하지 않았다.
- (A) 현재 동작이 맞다 → 웹 페이지 두 곳과 `member/CLAUDE.md`를 코드에 맞게 재작성.
- (B) "복구"가 기획 의도였다 → 북마크·Pick 리스너를 되돌리고 복구 경로를 구현.

**추가 정밀 지적** — 루트는 물리 삭제가 아니라 `deleted_at`만 설정된 채 행이 DB에 영구 잔존한다. 사용자 관점에서는 "영구 삭제"가 참이지만 저장 계층에서는 거짓이다. 개인정보 문구를 문자 그대로 참으로 만들려면 별도 purge가 필요하다.

### [B2] 스토어에 올릴 빌드가 개발 서버를 바라본다

```ts
// src/api/client.ts:18-21
export const BASE_URL =
  Platform.OS === "web" ? "" : (process.env.EXPO_PUBLIC_API_BASE_URL ?? "https://dev-api.moodi.kr");
```

`EXPO_PUBLIC_API_BASE_URL`을 주지 않으면 **릴리스 빌드도 `dev-api.moodi.kr`을 쓴다**. 주석이 밝히듯 현재 운영 서버(`api.moodi.kr`)가 존재하지 않아 테스트 트랙이 그렇게 동작해 왔다.

확인 결과 `eas.json`의 `production`·`production-upload-key` 프로필 어디에도 `env` 블록이 없다. 가정이 아니라 확정된 상태다 — 지금 그대로 스토어 빌드를 만들면 **반드시** 개발 서버를 바라본다.

출시 빌드가 개발 DB·개발 데이터를 그대로 쓰게 되므로, 심사 제출 전에 다음을 확정해야 한다.

1. 운영 API 호스트를 띄울 것인가, `dev-api`를 운영으로 승격할 것인가 — **제품·인프라 결정 사항**이다.
2. 결정한 호스트를 `eas.json`의 production 프로필에 `EXPO_PUBLIC_API_BASE_URL`로 주입.
3. 운영 호스트가 확정되면 위 폴백을 개발 전용으로 좁히거나, 값이 없을 때 빌드가 실패하도록 바꾸는 편이 안전하다.

## 2. 백엔드 설계·구현 문제

### [S1] 검색 응답이 로케일을 걸지 않아 목록은 한국어, 상세는 영어로 나갔다 — **수정 완료**

`SpotSearchService`가 `findBySpotIdIn(spotIds)`로 번역 행을 로케일 없이 집고 `(a,b)->a`로 접었다. 한 스팟에 여러 로케일 행이 있으면 아무 행이나 이겼다. 상세는 `SpotDetailReader.java:65`가 `findBySpotIdAndLocale(spotId, "en-US")`로 제대로 걸고 있어, 같은 스팟이 목록에서는 `협재해수욕장`, 상세에서는 `Hyupjae Beach`로 보였다(8개 스팟 전수 불일치 확인).

이것이 **앱의 영문 검색이 통째로 실패하던 근본 원인**이었다(아래 [S2]).

→ `findBySpotIdInAndLocale(spotIds, "en-US")`를 추가해 상세와 같은 기준으로 맞췄다.

### [S2] "비슷한 무드의 스팟"이 문자 그대로 무작위였다 — **수정 완료**

`SpotDetailQueryRepositoryImpl.java:40`이 `ORDER BY RANDOM()`이었고, 무드 태그가 **하나라도** 겹치면 후보였다. 같은 스팟을 4번 조회하면 4번 모두 겹치지 않는 결과가 나왔다.

```
call0: 15171,152,2275,10444,12698
call1: 8684,9842,7978,12389,8033
call2: 2288,1852,14521,14480,3400
call3: 939,11353,11986,14292,13357
```

화면에서는 제주 해수욕장의 "비슷한 무드"로 인천 모래내시장, 서울역 롯데아울렛 매장이 떴다. 추천이라고 내놓는 자리가 무작위인 것은 심사에서 지적받기 쉽다.

→ 겹치는 무드 태그 수 내림차순 → 저장 수 → id 순으로 결정적 정렬하도록 고쳤다.

### [S3] `saved=true`가 비로그인 요청에서 조용히 무시됐다 — **수정 완료**

`SpotSearchQueryRepositoryImpl.java:179-184`가 `if (saved && memberId != null)`이라, 토큰 없이 `saved=true`를 보내면 조건을 버리고 **필터 없는 목록과 완전히 동일한 응답**(전부 `bookmarked:false`)을 돌려줬다. 약속과 정반대인 응답이다.

→ `saved && memberId == null`이면 401로 끊는다.

### [S4] 공지 목록이 예약 발행을 무시했다 — **수정 완료**

`NoticeQueryRepositoryImpl`이 `visible` 불리언만 봤다. 미래 날짜로 잡아 둔 공지가 등록 즉시, 그것도 `publishedAt DESC` 정렬 탓에 **목록 맨 위**에 떴다. 약관(`Policy`)은 이미 `effectiveAt <= today`로 같은 규칙을 지키고 있어 도메인 간 규칙이 어긋나 있었다.

→ 공개 목록과 상세 모두에 `publishedAt <= today`를 걸었다(관리자 목록은 예약분을 계속 본다).

### [S5] 검색 `size`에 상한이 없었다 — **수정 완료(PR #93)**

`size=1000` → 1000행, `size=5000` → 1.8MB·3초 응답. 인증 없는 공개 엔드포인트에서의 자원 고갈 경로였다. → `Math.clamp(size, 1, 100)`.

### [S6] 잘못된 요청이 500으로 나갔다 — **수정 완료(PR #93)**

`/api/spots/abc`(타입 불일치), 없는 경로, 허용되지 않은 메서드 등 8종이 모두 500이었다. → 400/404/405로 분리.

### [S7] `PUT /api/routes/{id}` 저장이 500이었다 — **수정 완료(PR #92)**

`RouteSaveService.update`가 바뀐 Day를 새 `RouteDay`로 교체해 `uk_route_day_route_day_number` 유니크 제약을 위반했다. → 영속 Day를 재사용하고 `clearSchedule → flush → replaceSchedule` 순서로 교체.

### [S8] 카카오 길찾기 키가 배포에 전달되지 않았다 — **수정 완료(PR #92)**

`KAKAO_REST_API_KEY`가 `deploy.yaml`에도 GitHub 시크릿에도 없었다. 그 결과 모든 구간 이동시간이 0분·0m로 저장돼 앱에 표시되지 않았다. → 워크플로에 전달 + 시크릿 등록. REST 키로 도보·대중교통 API 200 확인(네이티브 키는 "KA Header is required"로 실패하므로 **REST 키여야 한다**).

### [S9] 문의 첨부 스토리지 비활성이 문의 **상세 조회 전체**를 죽인다 — 미수정

`gcs.inquiry-upload.enabled=false`(dev)에서 `UnavailableInquiryAttachmentStorage`가 업로드뿐 아니라 **읽기에도** 503을 던진다(`:10-18`). 상세 조회가 첨부 URL을 발급하는 구조라(`InquiryService.java:98-103`) 첨부가 1건만 있어도 본문·답변까지 통째로 실패한다.

**수정 방향** — 첨부 URL 생성 실패를 개별적으로 삼키고 `attachments: []`로 응답(본문·답변은 유지). 병행해 dev 버킷 활성화.

### [S10] `"Popular in {district}"`가 사실은 "id가 작은 순" — 미수정

`SpotDetailQueryRepositoryImpl.java:81`이 `ORDER BY (bookmark count) DESC, s.id ASC`인데, 표본 100개 중 북마크가 있는 스팟이 6개뿐이라 사실상 id 순이다. 인기도 신호(조회수·노출수)가 없으면 이 섹션은 인기와 무관하다.

### [S11] `INQUIRY_TOO_MANY_ATTACHMENTS`가 도달 불가 — 미수정

`@Size(max=5)`가 먼저 걸려 `INVALID_REQUEST`로 나간다(`InquiryCreateRequest.java:12-35`). 전용 에러 코드가 사문화됐다.

### [S12] 약관 API에 로케일 개념이 없다 — 미수정 ([P2]와 연결)

`notice`·`faq`·`policy` 어느 테이블에도 locale 컬럼이 없고 `?lang=`·`Accept-Language`도 받지 않는다(`V17`, `V18`, `V19`). 다국어를 전제한 디자인(정책 상세의 "A / 가" 토글)을 구현할 수 없는 상태다.

## 3. 기획 문서와 실제 동작의 불일치

### [P1] `member/CLAUDE.md`의 탈퇴 설계가 현재 코드와 다르다

문서는 탈퇴를 "복구 가능한 비활성화"로, `bookmark`·`route`·`pick_request`를 "유지"로 기술한다(`:231-243`). 실제로는 북마크·Pick이 하드 삭제된다. [B1]의 오염원이다.

### [P2] 서버에 등록된 "현행 약관"이 한국어·미완성인데, 앱은 자체 번들 영문 텍스트를 보여 준다

```
GET /api/v1/policies/TERMS_OF_SERVICE
→ content 1,018자, 한글 611자, "### **제1조 (목적 및 정의)**" 하나로 끝, 제2조 없음(문장 중간 종료)
GET /api/v1/policies/PRIVACY_POLICY
→ 404
```

앱은 이 API를 **한 번도 호출하지 않는다**. `getPolicies`/`getPolicy`/`loadPolicies`/`loadPolicy`가 `api/support.ts:57,66`과 `useSupportStore.ts:222-263`에만 존재하고 호출하는 화면이 0개다. `PolicyDetailScreen.tsx:55`는 번들된 영문 `TermsBody`를 렌더한다.

결과적으로 **심사자가 앱에서 읽는 문서와 서버에 등록된 문서가 서로 다른 문서**다. 약관 스토어 분기 전체가 죽은 코드다.

**주의** — 지금 앱을 서버 소스로 전환하면 심사자가 한국어 미완성 문서를 보게 된다. 순서는 반드시 (1) 로케일 컬럼 + 영문 전문 2종 등록 → (2) 앱 전환이다.

### [P3] 알림 화면은 서버 API가 없어 영구히 빈 화면이다

`useNotificationStore.ts:36`이 `items: []` 고정이고 대응 엔드포인트가 없다. 기획에 화면은 있으나 데이터 출처가 정의되지 않았다 — 출시 범위에서 뺄지, API를 만들지 결정이 필요하다.

### [P4] 출생연도·성별은 변경 API가 없다

서버는 온보딩에서 한 번만 받는다. 앱은 값을 기기에만 저장하고 그 사실을 토스트로 고지한다(`EditProfileScreen.tsx:159-171`). 디자인에는 이 두 행이 아예 없다. 기획상 "가입 후 수정 가능"이 맞다면 API가 필요하고, 아니라면 행을 빼는 것이 맞다.

### [P5] 무드 태그 표기가 엔드포인트마다 다르다

목록 응답은 `RIVERSIDE`, 상세는 `#Riverside`, 필터 파라미터는 **소문자만** 받는다(`moodTags=RIVERSIDE` → 0건). 앱은 `moodKey`로 흡수하고 있어 지금은 동작하지만, 계약이 깨지기 쉽다. 공유 커널 `MoodTag`에 `@JsonValue`/`@JsonCreator`를 붙여 한 표기로 통일할 것을 권한다.

## 5. 콘텐츠 공백 (심사 전 반드시 채울 것)

### [C1] 공지 0건, FAQ 1건

```
GET /api/v1/notices → {"items":[],"nextCursor":null,"hasNext":false}
GET /api/v1/faqs    → 카테고리 1개, 항목 1개
```

마이그레이션 V1–V28 전체에 `INSERT`가 없다. 모든 콘텐츠는 어드민 API로 수기 입력해야 한다. 디자인은 공지 4건·FAQ 3개 카테고리를 전제로 그려져 있다. 심사자가 반드시 열어 보는 화면이다.

### [C2] 스팟 카탈로그의 70%가 소매·체인 매장

표본 100개 중 70개가 `ZARA 서면점`, `올리브영…`, `NBA 롯데아울렛…` 같은 매장이다. [S2]의 무작위 추천과 겹치면 "여행 앱이 편의점을 무드 추천으로 내놓는" 화면이 된다. [S2]는 고쳤으므로 남은 것은 시드 데이터 정제다.

### [C3] 지역 자동완성 목록이 실제 데이터와 어긋난다

`GET /api/spots/search?area={한국어 시·도}` 를 16개 값으로 전수 실측했다(2026-09-16).

| 데이터 있음 (9) | 데이터 없음 (7) |
|---|---|
| 서울 · 부산 · 인천 · 대전 · 광주 · 제주 · 경주 · 전주 · 강릉 | 대구 · 울산 · 세종 · 광양 · 남해 · 청주 · 충청북도 |

그런데 앱의 번들 자동완성 목록(`AreaSearchField.AREA_INDEX` — 필터 시트, 루트 생성, 스팟 추천이 공유)은 정반대로 어긋나 있다.

- **죽은 항목을 제공한다**: `Namhae`, `Gwangyang`, `Cheongju, Chungcheongbuk-do`, `Jeungpyeong, Chungcheongbuk-do` 는 서버가 0건을 주는 시·도로 번역된다(`regionToArea` 가 칩의 마지막 세그먼트만 본다). `Seoul Forest` 는 아예 매핑이 없어 서버 필터가 걸리지 않는다. 사용자는 목록에서 고른 지역이 왜 빈 결과를 내는지 알 수 없다.
- **데이터가 많은 지역이 빠져 있다**: 제주·인천·대전·광주·전주·강릉이 목록에 없다. 특히 제주는 비회원 홈의 인기 스팟 상위를 차지하는 지역인데 지역으로 고를 수 없다.

근본적으로는 이 목록이 서버의 `GET /api/v1/picks/areas` 대신 하드코딩되어 있어서 생기는 문제다. 다만 그 엔드포인트는 문서와 달리 **컨트롤러 단위 `@LoginRequired`** 라 비회원에게 401 이므로, 번들 목록을 지우고 서버로 완전히 옮기려면 그 인증 범위부터 정해야 한다.

같은 죽은 값이 **두 군데**에 있었다. 공용 자동완성 목록(`AREA_INDEX`) 말고도 스팟 추천 화면이 자기만의 기본 제안 목록(`SpotRecommendScreen.POPULAR_AREAS`)을 따로 들고 있었고, 거기에도 `Cheongju, Chungcheongbuk-do` 가 들어 있었다. 첫 수정 뒤 브라우저로 확인하지 않았다면 그대로 남았을 항목이다.

**앱 쪽은 수정했다**([F6]) — 죽은 항목 5개를 빼고 데이터가 있는 6개 지역을 넣어 실측 결과와 맞췄으며, 추천 화면의 기본 제안 목록도 제주로 바꿨다. 다만 이것은 *지금의 데이터 상태*에 맞춘 목록이므로, **콘텐츠가 늘거나 줄면 다시 어긋난다**. 항구적 해결은 `picks/areas` 의 인증 범위를 정하고 목록을 서버에서 받는 것이다.

## 8. 조사했으나 결함이 아니라고 판정한 것

감사에서 지적됐지만 근거를 확인한 결과 고치지 않기로 한 항목이다. 나중에 같은 지적이 다시 올라올 수 있어 판정 근거를 남긴다.

### 코어 `Clipboard` import — 동작한다

`SpotDetailScreen.tsx:4,187` 이 `react-native` 에서 `Clipboard` 를 가져와 주소 복사에 쓴다. "제거된 API 를 쓰고 있어 복사가 조용히 실패한다"는 의심이 있었으나, 설치된 react-native 0.86 을 직접 확인한 결과 **여전히 동작한다**.

- `node_modules/react-native/index.js` 에 `get Clipboard()` 게터가 남아 있고, `'clipboard-moved'` deprecation 경고를 찍은 뒤 `./Libraries/Components/Clipboard/Clipboard` 를 require 한다.
- 그 디렉터리도 실제로 존재한다.

즉 경고만 나올 뿐 기능은 멀쩡하다. 권장 대체제인 `expo-clipboard` 는 **설치되어 있지 않다**. 경고 하나를 없애려고 출시 직전에 네이티브 의존성을 추가하는 것은 이득보다 위험이 크다고 판단해 그대로 둔다. RN 이 실제로 제거하는 버전으로 올릴 때 함께 옮기는 것이 맞다.

### 선택 모드의 "보이지 않는 흰 체크" — 의도된 표현

`SavedSpotGrid.tsx:166` 이 미선택 원(`rgba(255,255,255,0.7)`) 위에 `palette.white`(#FFFFFF) 체크를 그려 사실상 보이지 않는다. 그러나 이는 이 코드베이스의 일관된 규칙이다 — `Checkbox.tsx:81-85` 도 라이트 테마의 미체크 틱을 `neutralWhite` 로 그린다. **미선택은 빈 원으로 보이게 하는 것**이 표준적인 표현이고, 선택 시에는 보라색 원 + `#FCFCFC` 체크로 분명히 바뀐다. 해당 Figma 프레임 없이 뒤집을 근거가 없어 그대로 둔다.

### 남은 위험 (조치하지 않음, 근거 있음)

- **en-US 번역 행이 없는 스팟의 제목이 null 로 나갈 수 있다.** 키워드 없는 조회는 `locale='en-US'` 조인이 걸리지 않기 때문이다. 다만 현재 데이터로 **120개 스팟 전수 확인 결과 해당 사례 0건**이라 그대로 둔다. 콘텐츠가 늘면 다시 볼 것.
- `clearAll` 이 최대 500개 id 를 한 번에 DELETE 본문으로 보낼 수 있다. 다만 이 함수는 화면에 연결만 되어 있고 **호출되는 곳이 없다**(디자인에서 "Clear all" 이 빠졌다).

## 11. 2차 독립 검증 (배포 후) — **NOT COMPLETE**

머지·배포가 끝난 상태를 기준으로 두 번째 독립 검증을 돌렸다. 결과는 **NOT COMPLETE** 이며 5건이 올라왔다. 아래는 각 항목을 직접 재확인한 결과와 조치다.

### 확인 후 고친 것

**지역 제안을 눌러도 아무 일도 일어나지 않았다.** 제안 행을 누르면 `mousedown` 이 먼저 `blur` 를 일으켜 목록이 언마운트되고, 뒤이어 올 `onPress` 가 닿을 대상이 사라진다. 포커스 해제를 한 박자 늦춰 고쳤고, **웹에서 실제로 클릭해** 검증했다(mousedown 직후에도 행이 남고 칩이 추가된다).

**같은 버그가 두 곳에 있었다** — 공용 `AreaSearchField`(필터 시트·루트 생성)와, 그것을 쓰지 않고 지역 입력 UI를 따로 구현한 스팟 추천 화면. 이 저장소에서 지역 UI 중복을 발견한 것이 **세 번째**다(하드코딩 목록 두 벌 → 필드 구현 두 벌). 합치는 것이 근본 해법이지만 화면 구성이 달라 출시 직전 교체는 위험이 커 미뤘다. **다음에 지역 UI를 고칠 사람은 반드시 두 곳을 함께 봐야 한다.**

**검색창 자동완성이 서버 결과를 한 번 더 걸렀다.** 결과 화면에서 고친 것과 같은 문제가 검색 진입 화면에 남아 있었다. 서버가 주소로 잡아 준 제안이 조용히 사라져 "검색창엔 없는데 검색하면 나오는" 어긋남이 생긴다.

### 확인했으나 고치지 않은 것

**0건 검색이 요청을 9번 보낸다.** 검증자도 "동작은 정확하고 비쌀 뿐"이라고 적었다. 빈 상태 문구·폴백 모두 정상이고, 가장 중요한 수정([F1])이 든 파일을 다시 건드리는 위험이 이득보다 크다고 판단했다.

**`INQUIRY_TOO_MANY_ATTACHMENTS` 가 `@Size(max=5)` 에 가려 도달 불가**(`InquiryCreateRequest.java:24`). 앱이 첨부를 5개로 막고 있어 앱에서는 닿을 수 없는 경로다. 같은 DTO 의 제목·내용 `@Size` 도 똑같이 도메인 검증과 중복이라, 규칙 일관성을 이유로 고치려면 셋을 다 건드리고 REST Docs 스니펫까지 영향을 받는다. 백엔드 담당자의 설계 판단 영역이라 릴리스 브랜치에 넣지 않았다.

### 새로 확인된 문제

**[N1] 영문 설명에 한국어가 섞여 나간다 — 콘텐츠, 결정 필요**

9개 시·도 × 100건을 전수로 재면 **900건 중 31건(3.4%)** 의 `description` 에 한글이 들어 있다. 제목은 900건 전부 깨끗하다.

```
[12789] Hyupjae Cave      :: Discover the enchanting beauty of 협재동굴, ...
[8884]  CU Seomyeon Lotte :: ... at CU 서면롯데점, where trendy finds await.
[11517] ZARA Square One   :: ... at ZARA 스퀘어원점, where style meets urban energy.
```

지역별 분포: 제주 8 · 인천 5 · 부산 4 · 경주 4 · 강릉 4 · 대전 3 · 전주 3.

**중요한 관찰**: 남은 한국어는 대부분 **영어 이름이 존재하지 않는 브랜드·점포명**이다. 설명을 재생성해도 LLM 이 "CU 서면롯데점"을 영어로 바꿀 방법이 없다. 즉 이 문제는 [C2]("카탈로그 70% 가 소매 체인")와 **같은 뿌리**이고, 해법은 재생성이 아니라 **스팟 정제**다. 3.4% 의 설명을 앱에서 일괄로 감추는 것도 답이 아니다(설계상 한 줄 소개가 들어갈 자리가 빈다). 제품 결정 사항이라 임의로 정하지 않았다.

**[N2] 기존 루트의 이동 시간은 영원히 0 분이다 — 결정 필요**

[S8] 에서 카카오 키를 배포에 전달했지만, **구간은 저장 시점에만 계산된다**(`RouteSaveService.buildDays:226` → `calculateLegs:250`). 카카오 호출이 실패하면 `LegResult.unavailable()` 이 **0/0 으로 저장**되고(`:168`), 읽기 경로는 저장값을 그대로 돌려준다. 앱은 0/0 구간을 빈칸으로 그린다(`RouteCreateScreen.tsx:1171`).

따라서 **키가 없던 시절에 만들어진 루트는 스스로 낫지 않는다.** 사용자 우회책은 있다 — 루트를 편집 후 저장하면 다시 계산된다.

선택지: ① 전 구간이 0 인 루트를 일회성으로 재계산 ② 읽기 시 지연 재계산(모든 구간이 0일 때만). ②는 낫는 순간까지 상세 조회마다 카카오를 부르므로 성능 판단이 필요하다. 운영 판단이라 넘긴다.

**[N3] 안드로이드 패키지와 iOS 번들 ID 가 다르다 — 게시 후 변경 불가, 결정 시급**

```
android.package      : com.mudi
ios.bundleIdentifier : kr.moodi.app
```

`com.mudi` 는 오타로 보인다. **스토어에 한 번 게시되면 영구히 고정**되며 바꾸려면 새 앱으로 올려야 한다.

**이 워크플로로는 게시된 적이 없다** (2026-09-16 실행 로그 확인). `Play Store release` 6회 실행이 전부 같은 지점에서 멈췄다.

```
Looking up credentials configuration for com.mudi...
Google Service Account Keys cannot be set up in --non-interactive mode.
Error: build command failed.
```

자격증명 조회 단계에서 실패해 **빌드가 시작조차 못 했다** — AAB 가 만들어진 적이 없으니 제출도 없었다. 같은 로그에 `No environment variables with visibility "Plain text" and "Sensitive" found for the "production" environment on EAS` 도 찍혀 [B2]·[N6] 의 전제(production `env` 부재)가 함께 확인됐다.

따라서 **지금 바꾸면 비용이 거의 없다.** 다만 이 근거는 "이 워크플로로는 게시된 적 없음"까지이고, 누군가 로컬에서 `eas submit` 을 수동으로 돌렸을 가능성까지 배제하지는 못한다. Play Console 에 앱 레코드가 있는지만 확인하면 결론이 난다.

덧붙여 `eas.json` 의 `submit.production.ios.language` 가 `"ko"` 인데 앱 UI 는 전부 영어다.

**[N4] "비슷한 무드의 스팟"이 지역을 전혀 고려하지 않는다 — 제품 판단**

제주 스팟의 추천이 전부 부산으로 나오는 사례가 보고됐다. [S2] 수정은 **무드 일치도**로만 정렬하므로 이는 설계대로 동작한 결과다. 무드 추천에 지역 근접성을 섞을지는 제품이 정할 문제다.

### 측정 방법에 관한 경고

[N1] 을 처음 잴 때 Windows PowerShell 의 `Invoke-RestMethod` 로 900건을 훑어 **한국어 0건**이라는 결과를 얻었고, 하마터면 실재하는 결함을 근거 없이 기각할 뻔했다. 원인은 응답에 `charset` 이 없을 때 이 cmdlet 이 UTF-8 이 아닌 코드페이지로 디코딩해 한글이 깨진 문자로 바뀌는 것이다 — 그러면 한글 정규식이 아무것도 찾지 못한다.

**이 API 의 한국어 여부를 잴 때는 PowerShell 의 `Invoke-RestMethod` 를 쓰지 말고 `node` 의 `fetch`(항상 UTF-8)를 쓸 것.**

### 2차 검증에서 정상으로 확인된 것

영문 검색 정상 경로(`Hyupjae` → 폴백 없이 2회 호출, `3 Spots matching`), 단수 표기(`1 Spot matching`), 지역 값이 서버 데이터와 일치(데이터 있는 9곳 전부 결과 있음/죽은 7곳 전부 0건), `area=제주`·`area=인천` 필터 종단 동작, `Announcements` 헤더 일치, `Spots · N+` 복구, 11개 화면 × 라이트·다크 22회 렌더에 **빈 화면·크래시·콘솔 에러 없음**, 렌더된 UI 문자열에 한국어 없음.

## 12. 3차 독립 검증 — **NOT COMPLETE**

병합된 상태를 기준으로 세 번째 검증을 돌렸다. 2차에서 고친 두 건은 **독립적으로 PASS** 확인됐고, 회귀도 없었다. 판정을 뒤집은 것은 **새로 드러난 지도 문제**다.

### 2차 수정 재확인 (되돌리지 말 것)

지역 제안 탭은 `AreaSearchField` 를 쓰는 네 호스트 전부에서, 라이트·다크 모두 정상이다. 검증자는 `click()` 대신 **실제 `mouse.down` → 대기 → `mouse.up`** 으로 눌러(원래 버그를 가리지 않도록) 행이 mousedown 중에도 살아 있는지와 칩이 실제로 붙는지를 함께 확인했다. 칩 추가에서 멈추지 않고 Apply 까지 몰아 `keyword=cafe&area=부산` 요청 → 결과 3건이 **전부 부산**(비부산 유출 0)임을 네트워크로 확인했다. 검색 자동완성도 적중 시 요청 1회, 0건일 때만 2회로 정상이다.

화면 23개 × 라이트·다크 46회 로드: 페이지 에러 0, 콘솔 에러 0, 실패 요청 0, 깨진 이미지 0, 렌더된 DOM 텍스트에 한국어 0.

### [N5] 지도 기본 배경이 전부 한국어다 — 결정 필요

영어 전용 앱인데 모든 지도의 지명 라벨이 한글이다(평양·인천·대전·대구·부산·제주특별자치도·강원도·남해). 스팟 상세에서는 영문 주소 바로 아래 지도에 `파리바게뜨` 가 찍힌다.

**앞선 두 라운드가 이걸 놓친 이유가 중요하다.** 지도 라벨은 DOM 텍스트가 아니라 **래스터 타일**이라, 지금까지 돌린 한글 스윕이 전부 `hangul=0` 으로 통과시켰다. 텍스트 기반 점검으로는 구조적으로 볼 수 없는 영역이다.

Kakao JS SDK 에는 영문 배경지도 옵션이 없다. 선택지는 ① 라벨이 있는 다른 제공자(Google·Naver 등 `language` 옵션 지원) ② 라벨 억제 ③ 현행 유지다. **이 항목은 지금까지 한 번도 결정권자에게 올라간 적이 없다.**

### [N6] 출시 빌드의 지도가 `http://localhost:8081/` 을 문서 origin 으로 쓴다 — 결정 필요

```ts
// src/config/kakao.ts:26
export const KAKAO_WEBVIEW_BASE_URL =
  process.env.EXPO_PUBLIC_KAKAO_WEBVIEW_ORIGIN ?? "http://localhost:8081/";
```

같은 파일 주석이 이유를 밝힌다 — 2026-09-09 기준 이 Kakao JS 키에 **등록된 도메인이 `http://localhost:8081` 하나뿐**이고 `dev-api.moodi.kr`·`moodi.kr`·vercel 은 "domain mismatched" 401 이다. 부주의한 폴백이 아니라 지금 동작하는 유일한 origin 이다. 그리고 `eas.json` production 에 `env` 가 없으니 이 값이 그대로 스토어 빌드에 실린다 — [B2] 와 **같은 원인의 세 번째 결과**다.

실측(스팟 상세 지도 화면, 외부 요청 26건):

| 프로토콜 | 건수 | 호스트 |
|---|---|---|
| **평문 http** | **11** | `t1.daumcdn.net` 5, `mts.daumcdn.net` 6 |
| https | 15 | `storage.googleapis.com` 14, `dapi.kakao.com` 1 |

타일만이 아니라 **지도 런타임 스크립트 자체**가 평문이다(`http://t1.daumcdn.net/mapjsapi/js/main/4.5.26/kakao.js`). `app.json` 에는 `ios.infoPlist` 가 **아예 없어** ATS 예외도 없다. 따라서 iOS 에서는 타일이 빠지는 정도가 아니라 **지도가 초기화되지 못할 가능성이 크다.**

**해결 방법이 확정됐다 — ATS 예외는 필요 없다.** (2026-09-16 실측)

Kakao 자원이 HTTPS 로도 모두 제공되는지 직접 확인했다.

| 자원 | HTTPS 응답 |
|---|---|
| SDK 로더 `dapi.kakao.com/v2/maps/sdk.js` | 200 |
| 런타임 스크립트 `t1.daumcdn.net/mapjsapi/js/main/4.5.26/kakao.js` | 200 |
| 타일 `mts.daumcdn.net/api/v1/tile/...` | 200 |
| 이미지 자원 `t1.daumcdn.net/mapjsapi/images/...` | 200 |

결정적으로 **로더 스크립트에는 하드코딩된 `http://` 참조가 하나도 없다.** `"//t1.daumcdn.net"` 처럼 **프로토콜 상대** 경로를 쓰므로 SDK 는 문서의 프로토콜을 그대로 따라간다. 즉 평문으로 내려받던 것은 순전히 문서 origin 이 `http://localhost:8081/` 이었기 때문이다.

따라서 **`EXPO_PUBLIC_KAKAO_WEBVIEW_ORIGIN` 에 HTTPS 도메인을 넣으면 모든 자원이 HTTPS 로 따라온다.** `NSAllowsArbitraryLoadsInWebContent` 같은 보안 완화는 필요 없다. 남은 작업은 두 가지뿐이다.

1. Kakao Developers 에 HTTPS 도메인을 등록한다(콘솔 작업).
2. 그 도메인을 `eas.json` production 의 `env` 에 넣는다 — [B2] 와 같은 자리다.

**미검증**: 실기기 WKWebView 동작은 확인하지 못했다. 다만 위 실측으로 원인과 해법이 특정됐으므로, 실기기 확인은 "고친 뒤 확인"의 성격이 됐다.

### [N7] 로마자 표기가 스스로 어긋난다 — 콘텐츠

스팟 상세 제목은 `Hyupjae Beach` 인데 같은 화면의 AI 설명은 `Hyeopjae Beach` 라고 쓴다. [N1]·[C2] 와 같은 계열이다.

## 13. 4차 독립 검증 (로그인 회원 영역) — **COMPLETE**

1~3차는 **전부 게스트로만** 돌았다. 회원 전용 화면은 한 번도 검증된 적이 없어 4차를 그 영역에만 집중시켰다. 판정은 **COMPLETE** — 기능 파손은 없고, 코드로 고칠 수 있는 사소한 결함 두 건이 나왔으며 둘 다 고치고 런타임으로 확인했다.

### 이 라운드에서 처음 실행된 것

**닉네임 편집 8개 분기 전부.** 회원이 그 행을 누를 수 없던 시절([M1])에는 `UsernameSheet`·중복 사전확인·`DUPLICATE_NICKNAME`/`INVALID_NICKNAME` 인라인 분기가 **도달 불가능한 죽은 코드**였다. 이제 전부 동작하며, 실패해도 상태가 남지 않는다(행은 옛 값 유지, 시트 유지, 입력 보존).

그 밖에 저장 스팟(그리드·지도·클러스터링·선택/전체선택·단건/다건 삭제·확인 얼럿·지역/무드 필터·정렬·잘림 표시), **Add Spots 의 필터 시트**(3차가 닿지 못한 네 번째 `AreaSearchField` 호스트 — 제안 탭 정상, 라이트·다크 모두), 루트(목록·상세·편집·복제·공유, 이름 변경이 상세·목록·Discover 카드까지 전파되어 **캐시가 남지 않음**), MY 탭·알림·로그아웃·국가 변경, 계정 삭제(성공 및 400 실패 시 세션 보존·거짓 삭제 메시지 없음).

### 고친 것

**[F8] 루트 상세 케밥 메뉴에 접근성 이름이 없었다.** `Header` 의 `defaultIconLabel` 에 `more` 항목이 없어 폴백 `"Header action"` 이 그대로 나갔다. 루트 목록 카드는 이미 `"More options for ..."` 라 표기도 어긋나 있었다. 표에 한 줄을 더해 `Header` 를 거치는 `more` 버튼(루트 상세의 일반·지도확장 두 헤더)을 한 번에 고쳤다. 브라우저에서 확인: 버튼 이름에 `More options` 가 있고 `Header action` 은 사라졌다.

**[F9] 저장 목록 잘림 표시가 루트 없는 회원에게 보이지 않았다.** 이는 **[F4] 수정의 사각지대**였다 — 잘림을 알리는 `+` 를 "루트가 1개 이상일 때만 뜨는" 전환 칩 줄 안에 넣었기 때문이다. 전환 줄을 무조건 띄우면 디자인 의도를 어기므로, 루트가 없고 잘렸을 때만 한 줄로 알린다. 상한은 스토어에서 파생 상수로 내보내 문구와 실제 값이 어긋나지 않게 했다.

검증(스텁으로 상한 조건을 인위적으로 만듦): 루트 없음 → 북마크 요청 **정확히 10회**(상한) 후 안내문 표시, 칩 없음 / 루트 있음 → `Spots · 500+` 칩 표시. 서버가 계속 "더 있다"고 답하는 조건에서도 **루프가 상한에서 멈추는 것**까지 함께 확인됐다.

### 방법론 경고 — 스텁이 만든 오탐

검증자가 "앱 결함"으로 보였던 네 건을 스스로 뒤집었다. 비-UUID 루트 id 를 넣어 로컬 루트 경로로 빠진 것, `/feed/popular-spots` 를 페이지 객체로 답해 `applyBookmark` 가 터진 것, 픽스처에 영문 `area` 를 넣은 것(앱은 한국어를 보낸다), 저장 지도의 밝은 배경(Kakao 는 타일 스타일이 하나뿐이라 디자인대로다). 나 역시 같은 함정을 한 번 밟았다 — 케밥 검증에 비-UUID id 를 써 **화면이 뜨지도 않았는데 판정을 시도**했다.

**교훈**: 회원 화면 검증은 전부 픽스처 기반이라 **실서버와의 필드 형태 불일치를 가릴 수 있다.** 그리고 "찾으려던 요소가 없음"과 "화면 자체가 안 뜸"을 반드시 구분해야 한다.

### 이 라운드가 남긴 확인 항목 (실기기·실계정 필요)

실제 Google/Apple 로그인과 토큰 수명, 진짜 401 → 재발급 → 로그아웃 경로, 네이티브 `expo-secure-store` 토큰 저장(웹은 AsyncStorage 였다), OS 공유 시트와 `moodi://route/shared/{id}` 딥링크, 실서버 대상 계정 삭제, 네이티브 WebView 의 지도([N6]), 사진 추천.

또한 알림 화면은 **서버 엔드포인트가 아예 없어** 영구히 빈 상태다. 코드 결함은 아니지만 심사자가 미완성으로 읽을 수 있다 — 제품 판단이 필요하다.
